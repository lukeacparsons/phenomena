**VO Barna SEO and GEO audit — 19 November 2026**

VO Barna’s largest search opportunity is to publish its existing film, screening and cinema information as readable, linked HTML pages with persistent identities. The current interface has useful data and working browser tools, but most of that information is unavailable until JavaScript runs or someone opens a dialog. Improving this foundation should precede additional AI-specific integrations.

The primary audit covers this checkout and the running preview at `http://127.0.0.1:8765/cinemas.html`. The related live host, `https://phenomenarapida.com`, serves the original Phenomena page; `/cinemas.html` and `/webmcp.html` return 404 there. These results do not establish whether VO Barna is published on another domain. No authenticated search-console, analytics or verified crawler-log data was inspected, so this is a technical and content-readiness audit rather than a ranking or traffic assessment. [Captured HTTP and browser evidence](seo-geo-audit-evidence-2026-11-19.json).

**The research supports HTML availability, useful content and clear navigation.** Google can render JavaScript, but explicitly recommends server rendering or prerendering because some bots cannot. Build-time static generation and request-time server rendering can both satisfy this requirement; a `.html` filename alone does not. The practical acceptance criterion is that a fresh HTTP response contains the page’s main facts and links without executing scripts. [Google JavaScript SEO guidance](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics).

Google’s July 2026 guidance treats GEO as part of SEO and emphasizes distinctive, useful content. It says Google Search does not use `llms.txt` for ranking and requires neither special AI schema nor artificial content chunking. Readability and semantic markup remain worthwhile, without any promise that a particular heading pattern produces citations. [Google generative AI optimization guidance](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide).

Bing similarly recommends clear headings, tables, evidence, freshness and consistent entity descriptions. For this site, the useful application is explicit cinema, room, film, language and screening information with dated sources. This is a content-design recommendation, not a claim that layout alone raises AI rankings. [Bing guidance and citation reporting](https://blogs.bing.com/webmaster/2026/2/Introducing-AI-Performance-in-Bing-Webmaster-Tools-Public-Preview/).

The stored snapshot contains 276 films, 2,806 screenings and 23 directory entries, generated at 16:33 UTC on 19 November. The browser shows fewer future screenings as sessions begin. The existing strengths are worth preserving: exact-ID film matching, merged-ID aliases, source URLs, screening timestamps with offsets, language/version evidence, cached availability timestamps, and a genuinely static WebMCP guide. These reduce the work needed to publish trustworthy pages.

**Generate the public pages from the same data that powers the interface.** Extend the existing collection pipeline with a separate rendering step after successful validation. Generate HTML, JSON-LD, sitemap and redirect mappings from one shared content model. Publish a complete version atomically and retain the previous version when collection or rendering fails. Never make a visitor or crawler wait for a cinema-provider scrape.

Keep schedule collection, ratings and seat freshness distinct. The local server schedules seat and rating refreshes, while new programme announcements currently need `preview:refresh`. Production needs an explicit background programme-refresh schedule, expiry processing and monitoring. Regenerate pages when their relevant content changes; do not claim every cinema has just been verified because the global build succeeded.

Use the existing visual design with progressively enhanced HTML. Film links should work as ordinary navigation with scripts disabled; JavaScript may intercept ordinary clicks to open a dialog while preserving middle-click, new tabs and back navigation. The destination must still render independently. A visible directory and finite pagination can expose the whole catalogue without putting thousands of showtimes on the homepage. A small `<noscript>` apology or an HTML list of links alone would not meet the requirement for readable film and cinema details. Google’s link guidance specifically favors actual anchors with resolvable `href` values. [Crawlable links](https://developers.google.com/search/docs/crawling-indexing/links-crawlable).

**Give each page type a clear purpose.** These are proposed routes on the future production origin, not existing URLs.

| Page | Example path | Main visitor information |
| --- | --- | --- |
| Current programme | `/en/` | Original-language cinema in Barcelona, dates, current films, coverage and venue links. |
| Cinema directory | `/en/cinemas/` | Named venues, municipalities, neighborhoods and links to their profiles. |
| Cinema profile | `/en/cinemas/phenomena-experience/` | Address, programme, rooms, formats, transport, accessibility, pricing context and official links. |
| Film | `/en/films/dune-1984/` | Correct film identity, year, useful facts and upcoming screenings grouped by date and cinema. |
| Other adaptation | `/en/films/dune-2021/` | A separate film identity; never merged into the 1984 film’s page. |

Individual screening pages are a later decision. If built, make each page useful on its own and preserve its identity when the start time changes. A proposed shape is `/en/screenings/dune-2021-phenomena-s-7k2m/`, where the final token is an immutable internal screening key. The example does not assert that this screening exists. Dates and times belong prominently in the page content; omitting them from the slug avoids URL churn after rescheduling.

**Adopt a written slug policy before publishing.** Google recommends readable words, hyphen-separated terms, a consistent case policy and avoiding needless parameters. Unicode URLs are valid; ASCII transliteration is an operational choice for this project, not a Google requirement. [Google URL guidance](https://developers.google.com/search/docs/crawling-indexing/url-structure).

The following rules are proposed project conventions:

1. Store an immutable internal entity ID separately from the slug. Use a persistent registry of `entity_id`, `locale`, `canonical_slug`, `aliases`, and publication status. Provider IDs and IMDb IDs are identity evidence or aliases; later enrichment must not silently change the public URL.
2. Choose a reviewed base name when publishing. Films use the established display title and verified original release year, such as `dune-1984`. Remove duplicated display-year suffixes before adding the year. Do not use a screening year, re-release date or guessed release year. If the release year is unknown, use the title and a stable discriminator only when necessary.
3. Keep film, special edition, festival event and double-bill identities distinct. The existing Dune double bill must not collapse into either individual film’s page. Omit session-specific `VOSE`, room, price and format labels from an ordinary film slug. A separately established edition may retain its distinguishing name.
4. Normalize Unicode, lowercase, map accented Latin letters to their base letters, and apply a reviewed transliteration map for characters that do not decompose. Delete apostrophes within words, turn other punctuation and whitespace into hyphens, collapse repeated hyphens and trim the ends. Preserve meaningful numbers and words; avoid blanket stop-word removal. A proposed validator is `^[a-z0-9]+(?:-[a-z0-9]+)*$`.
5. Transliteration examples under this policy: `Kinépolis Splau` → `kinepolis-splau`; `Mooby Glòries` → `mooby-glories`; `L’Hospitalet de Llobregat` → `lhospitalet-de-llobregat`; `Dune: Part Two` with verified year 2024 → `dune-part-two-2024`. Prefer an established English title for non-Latin titles on EN pages. Require a reviewed transliteration or override instead of dropping all characters into an empty slug.
6. Enforce uniqueness within each locale and entity type, reject empty slugs, and reserve routing names such as `search`, `page`, `new` and `index`. Film year and cinema municipality are useful semantic disambiguators. If ambiguity remains, append a short stable internal token. Never assign `-2` or `-3` based on scrape order, and never silently overwrite a collision. Set a project length guard, for example 100 characters per entity slug, with reviewed shortening rather than blind truncation; this is not a search-engine limit.
7. Freeze a published slug. Title corrections, translations, operator rebrands and improved metadata normally update the page while its URL stays stable. A genuine move gets a permanent server redirect from every former URL to the current canonical URL. Persist aliases across refreshes and avoid redirect chains or loops. Never reuse an old URL for a different film or venue.
8. Choose one HTTPS origin and a trailing-slash convention. Redirect supported equivalent case, slash and former-path variants once; generate only canonical forms in links and sitemaps. Do not change established URLs merely to make a slug cosmetically better.
9. Keep search/filter state separate from entity identity. Parameters are acceptable for searches, date ranges and combinations of venues or formats. Stable identity pages should have readable paths. Do not create an indexed page for every possible filter combination.
10. Give language versions explicit paths. For example, `/en/films/dune-2021/`, `/es/peliculas/dune-2021/`, and `/ca/pellicules/dune-2021/`. Localize route nouns and genuine title variants at first publication; keep proper names recognizable. Use a lookup table, never derive another language’s URL by guessing its translation.

Permanent redirects, canonical annotations and sitemap URLs should agree. Canonicals are signals for equivalent or very similar content, so a film page should not canonicalize to the homepage. Every translated page should normally self-canonicalize and link to its translated equivalents. [Canonicalization guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls).

For old query links, resolve `film` and `screening` through the persistent alias registry before redirecting. Preserve any still-useful selection state. Retain a valid film page when it has no upcoming screenings, with an explicit status and relevant alternatives. A genuinely unknown entity returns 404; intentionally removed content can return 410. Do not turn every expired link into a homepage redirect. Archive screening pages only when the retained information serves visitors; exclude expired sessions from the current-events sitemap.

**Make the content understandable without relying on appearance.** Use a descriptive H1, a short explanation, and headings such as “Upcoming screenings”, “Audio and subtitles”, “Screens and sound”, “Accessibility”, “Getting there”, and “Sources and last checked”. Use `<dl>` for labeled facts, real headings for sections, and tables with header cells where people need comparisons. Use `<time datetime>` with an explicit date and the correct Europe/Madrid offset. A heading hierarchy supports navigation; it is not a magic ranking factor.

On a film page, put the complete film name and year near the start. Label director, runtime, original language and translated titles separately. Each session should identify cinema, municipality, auditorium if known, absolute date, local time, screening audio, subtitle language, format and booking destination. The current film-level original language does not prove the audio of every session. Explain VOSE and VOSC, and keep unknown audio unknown. “Original version” must not become a synonym for “English”.

On a cinema page, publish reviewed research that answers practical questions. Distinguish cinema-wide features from room-specific features, current measurements from historical figures, and verified room identities from unmapped placeholders. Show units, source links and check dates next to facts. Treat advertised screen dimensions, inferred dimensions and independent measurements as different evidence. Do not turn the current “big screens only” selection, which includes comfort-focused venues, into an unsupported largest-screen ranking.

Prices need currency, ticket category, applicability and observation date. Seat counts need their observation time and meaning; stale cached counts should not be described as live availability. Keep accessibility evidence specific to the venue or room and retain conflicting or unresolved source information where it affects a visit. This labeling is especially valuable when a passage is quoted outside its original page.

Add a visible explanation of who runs VO Barna, how information is collected and checked, its independence from cinema operators, how to request corrections, and the limits of coverage. Source attribution should accompany material claims rather than only appear in a general footer. The distinctive editorial opportunity is a reliable comparison of Barcelona cinemas and their rooms, using the repository’s research and verified observations; generic rewritten film summaries add less value.

**Complete the language and metadata model together.** Google recommends different URLs for different languages because cookie- or browser-dependent variations may not all be crawled. Use ordinary language-switch links and reciprocal `hreflang="en"`, `es`, `ca`, plus a suitable `x-default` fallback. Translate substantive page explanations and metadata, not only buttons. Keep the language chosen by the URL when visited directly. [Multilingual site guidance](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites).

Suggested English homepage title: `Original-language cinema in Barcelona | VO Barna`. Suggested description: `Find original-language film screenings in Barcelona and nearby cinemas. Compare dates, venues, audio, subtitles and formats, then book with the cinema.` Film titles should identify the work and year, for example `Dune (1984) screenings in Barcelona | VO Barna`. Generate concise, accurate titles and descriptions per page; avoid a rigid character-count promise. Add matching Open Graph/social metadata for sharing, while treating it separately from a guaranteed ranking benefit.

**Use structured data to label the same visible facts.** Add a small connected JSON-LD graph with stable identifiers. Proposed mappings are `WebSite` and the actual publisher on the homepage, `MovieTheater` on venue profiles, `Movie` on film pages, `BreadcrumbList` where breadcrumbs are visible, and `ScreeningEvent` for individual screenings. Do not represent VO Barna as the owner of listed cinemas. Schema.org’s `ScreeningEvent` supports `workPresented`, `subtitleLanguage` and `videoFormat`, which map well to this catalogue. [ScreeningEvent vocabulary](https://schema.org/ScreeningEvent).

Only include verified values that the page exposes. Use actual event times and official booking URLs; omit unknown prices, availability, room identities or exact language values. JSON-LD can be generated directly into static HTML without requiring JavaScript execution. It does not replace the human-readable page.

Schema validity and Google rich-result eligibility are different. Google’s event experience requires a unique page focused on each event; a schedule containing many events does not meet that requirement merely by containing Event markup. Its documented availability includes Spain in Spanish. Make event pages a deliberate later investment and validate representative pages; do not promise rich results. [Google event requirements](https://developers.google.com/search/docs/appearance/structured-data/event).

Keep IMDb, Rotten Tomatoes and FilmAffinity scores clearly attributed as external ratings. Do not turn imported scores or third-party review snapshots into VO Barna’s own `AggregateRating` to seek stars: Google’s review-snippet rules prohibit aggregating ratings from other websites. [Review markup guidelines](https://developers.google.com/search/docs/appearance/structured-data/review-snippet).

**Define which URLs should be discovered and indexed.** Put canonical, useful, indexable pages in the XML sitemap. Use accurate `lastmod` values tied to substantive changes, and keep the current programme fresh without changing every historical page’s timestamp. Google ignores sitemap `priority` and `changefreq`. [Sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap).

Index reviewed cinema pages, useful film pages and a small number of genuinely helpful guides. Exclude arbitrary internal search results, empty combinations, demos and layout experiments from the index and sitemap. Use `noindex` on crawlable pages when exclusion is intended; blocking their crawl in robots.txt prevents crawlers from seeing that instruction. Canonicalize tracking or sorting duplicates only to an actually equivalent page. [Noindex guidance](https://developers.google.com/search/docs/crawling-indexing/block-indexing).

Allow intended search crawlers through both robots.txt and hosting protections. OpenAI documents `OAI-SearchBot` as the search crawler and `GPTBot` as a separate training crawler, with independent controls. Allowing search need not imply allowing training. Verify real crawler access using published identification information and logs; a successful request using a spoofed user-agent would not prove genuine bot access. [OpenAI crawler documentation](https://developers.openai.com/api/docs/bots).

For Google, verify the production property’s Search generative AI inclusion setting, including inherited settings. The default is inclusion; the control documentation says it rolled out globally on 31 August 2026. No account setting was inspected or changed in this audit. [Current inclusion control](https://support.google.com/webmasters/answer/16908024).

Keep the static WebMCP guide and tool integration as an additional way to use the site. Update tool-returned URLs to the same canonical film and screening routes. Tools that register after programme loading do not replace public page discovery. Treat `llms.txt` as optional documentation for a known consumer, after the ordinary website works.

**Deliver the improvements in this order.**

1. **Foundation, larger effort:** agree the public origin and URL registry; persist entities and aliases; add generated listing, film and cinema pages; use real internal links; ensure deployment includes generated data and HTML despite `static/preview-data/` being Git-ignored. Automate programme refresh and atomic publication. The current local server rejects directories, so trailing-slash pages also need explicit local routing rather than merely writing `index.html` files.
2. **Launch completeness, medium effort:** add contextual metadata, canonical/redirect behavior, real 404s, sitemap, crawler policy, no-JavaScript navigation and freshness notices. Publish the EN/ES/CA routes that have complete translations, then connect their alternates.
3. **Useful depth, medium editorial effort:** publish the best-supported cinema profiles first, then room comparisons and version/format guides. Add conservative JSON-LD and source/methodology pages. Review records before publishing; 202 room records do not imply 202 publishable room pages.
4. **Measurement and refinement, ongoing:** verify indexing and rendered HTML, measure mobile page experience, inspect search demand, and decide whether individual screening pages justify the maintenance cost. Consider IndexNow notifications for substantive changes after stable URLs exist, as recommended by Bing for participating engines.

Acceptance checks should verify outcomes: a direct film URL contains its title and screenings without scripts; a direct cinema URL contains its address, facts and film links; every intended indexable entity is reachable through ordinary links; all canonical destinations resolve; aliases survive an identity merge and schedule refresh; slugs do not change after a title correction; unknown entities return 404; expired films retain truthful pages; and locale alternates resolve reciprocally. Validate structured data against the visible page. Test missing-data and stale-data states as well as successful refreshes.

After launch, compare indexed canonical pages, crawl/rendering errors, organic landing pages and outbound official-ticket clicks. Google now documents a Generative AI performance report for impressions in AI Overviews and AI Mode, which may remain unavailable until sufficient impressions exist. [Google AI performance report](https://support.google.com/webmasters/answer/16984139). Use Bing’s AI Performance report for cited URLs and grounding queries, and track identifiable AI referrals separately. Referral traffic does not measure all citations. Neither dashboards nor manual prompt samples justify a promised uplift before baseline data exists.

The first implementation milestone should be a fully readable homepage, a cinema directory and reviewed cinema pages, plus persistent film pages linked from the listings. That establishes the pages search engines and answer systems can discover, understand, revisit and cite.
